这是一个非常实际且重要的问题。

简短回答：
不，你完全不需要一直连接远程生产服务器。 尤其是考虑到你拥有一台配置极高（13900K + 80G 内存）的本地电脑，利用本地开发环境不仅能让你离线工作，还能利用你的硬件优势实现秒级响应的调试体验。

我们将这分为数据库和图片存储两部分来解决：

1. 数据库：使用 Supabase CLI 本地版 (强烈推荐)

Supabase 最棒的一点就是它开源且提供了完美的本地开发工具链。你可以在本地 Docker 容器中运行一个和云端一模一样的 Supabase 实例。

你的 13900K + 80G 内存将在这里大杀特杀：

你可以在本地同时运行 Postgres、API 服务器、Auth 服务，几乎不占用你的资源，而且查询速度是 0ms 延迟。

操作步骤：

安装 Docker Desktop (Windows/Mac)。

安装 Supabase CLI: npm install -g supabase

初始化项目: 在你的 Next.js 项目根目录运行 npx supabase init。

启动本地环境: 运行 npx supabase start。

这会自动下载并启动 Postgres, Auth, Storage, Studio (管理面板) 等 Docker 容器。

启动后，控制台会给你一套本地的 URL 和 Key：

API URL: http://127.0.0.1:54321

DB URL: postgresql://postgres:postgres@127.0.0.1:54322/postgres

Studio URL: http://127.0.0.1:54323 (这是一个本地版的网页管理后台，非常好用！)

2. 图片存储：混合策略 (Hybrid Strategy)

图片文件有 100GB+，把它们全部下载到本地做测试是不现实的，也没必要。

推荐采用 "本地数据库 + 远程/本地混合图片" 的策略：

方案 A：在线开发模式 (推荐，最省事)

数据库：连本地 Docker (快，安全)。

图片：连远程 Cloudflare R2 (或者直接引用线上链接)。

原理：

你在本地数据库里插入几条测试数据，其中 storage_key 填写真实的 R2 路径。

前端 <Image src="https://r2.yourdomain.com/..." /> 是由浏览器去请求图片的，不是由你的本地 Next.js 服务器去下载转发（因为我们设置了 unoptimized）。

结果：只要你电脑能上网，开发体验和线上一样，而且不需要下载 1TB 图片到硬盘。

方案 B：完全离线/占位符模式 (最快，无需网络)

如果你的网速只有 100Mbps，加载高清大图觉得卡，或者想完全离线开发：

准备“样本数据”：

挑 50 张典型的素描图，放在 Next.js 的 public/sample-images/ 文件夹里。

数据填充 (Seeding)：

写一个 seed.ts 脚本，往本地 Supabase 插入 50 条数据。

把这些数据的 storage_key 指向本地：http://localhost:3000/sample-images/01.webp。

前端适配：

前端代码不需要改，因为它只是把 URL 拼接到 <Image src={url} /> 里。

本地测试时，图片秒开。

3. 最佳实践流程图

利用你的硬件优势，我建议的开发工作流如下：

环境准备:

开启 Docker Desktop。

终端运行 npx supabase start (利用 80G 内存，这会非常丝滑)。

数据同步 (Schema):

你在本地修改表结构 (比如加个字段)。

测试没问题后，运行 npx supabase db diff 生成迁移文件 (migration.sql)。

上线时，GitHub Actions 自动把这个 SQL 应用到远程 Supabase。

日常编码:

Next.js (npm run dev) 连本地 Supabase。

图片加载使用 方案 A (远程 R2)。虽然你网速慢，但浏览器会有缓存，加载过一次就不卡了。

如果断网，切换到 方案 B (本地样本图)。

总结

数据库：必须本地化。用 Docker 跑 Supabase，充分利用你的 CPU 和内存，实现零延迟交互，且不用担心误删线上数据。

图片：不需要本地化。让浏览器直接去 Cloudflare R2 拿。如果不联网，就用几十张本地样本图代替即可。

这样，你的开发环境既轻量（不需要下 1TB 数据），又高性能（数据库在本地内存里跑）。
